# 한국 트렌드 레이더 — 1단계: 뉴스 헤드라인 키워드 수집

언론사 분야별 RSS(정치 제외)에서 헤드라인의 명사와 2~3어절 조합을 뽑아 **키워드별 일일 등장량**을 장기 보관합니다.
헤드라인 원문은 저장하지 않습니다. 네이버 쇼핑과 YouTube는 이번 단계에 포함하지 않습니다.

## 구조


## 시작하는 순서

1. 이 폴더의 내용을 저장소 루트에 올립니다. 기존 루트의 v1 파일(`scripts/`, `config.json`, `docs/`, `.github/workflows/update.yml`)은
   `archive/v1-naver-search/` 와 겹치므로 **루트에서는 지웁니다.** 그래야 v1의 예약 실행이 멈춥니다.
   v1 의 실제 데이터 `docs/data.json` 은 삭제하지 말고 `archive/v1-naver-search/docs/` 로 옮깁니다 (GitHub 웹에서 파일 편집 → 파일명에 새 경로를 입력하면 이동됩니다).
   `docs/index.html` 은 이 패키지의 임시 안내 화면으로 덮어씁니다.
2. Settings → Actions → General → Workflow permissions 를 **Read and write** 로 설정합니다.
3. Actions 탭 → **Probe RSS feeds** → Run workflow. 결과 표(실행 요약)와 `probe-report` 아티팩트가 나옵니다.
   `실패`·`정지 의심` 피드는 `config/feeds.yaml` 에서 `enabled: false` 로 바꿉니다.
4. Actions 탭 → **Collect news keywords** → Run workflow 로 첫 수집을 확인합니다. 이후 자동 실행됩니다(아래 "예약 실행 구성" 참고).

## 동작 방식

- **날짜 없는 피드**: 한겨레·세계일보 피드는 기사 시각이 없다. 처음 본 제목 해시를 7일간 기억해 이튿날 다시 세지 않는다.
- **시간대 표기 없는 피드**: 한국 시각을 시간대 없이 적는 피드(프레시안·시사저널·통일뉴스·일다)는 UTC 로 읽혀 9시간 앞선다. `feeds.yaml` 에 `naive_kst: true` 로 표시한 피드는 항상 9시간을 되돌린다. 표시가 없는 피드는 최근 기사의 25% 이상이 미래일 때만 자동으로 되돌린다(안전망). 새 피드를 추가할 때 probe 의 "최신기사(시간 전)"가 음수로 나오면 이 표시를 붙인다.
- **수집 주기**: 매시간(`17 * * * *`). GitHub 예약 실행은 지연·누락되어 2시간 설정에서도 4~7시간 간격이 관찰됐기 때문에 촘촘하게 잡았다. 실제 간격은 `days.csv` 의 `max_gap_h` 로 확인한다. RSS는 최근 기사 수십 건만 보여 주고, 연예 피드는 3시간 분량뿐이라 하루 한 번으로는 놓칩니다.
- **중복 제거**: 정규화한 제목의 해시로 같은 기사를 한 건으로 셉니다(통신 기사가 여러 매체에 실려도 1건). 매체 수(`outlets`)는 따로 셉니다.
- **키워드**: 어절 안에서 이어진 명사 묶음과 구성 명사, 그리고 이어진 2~3어절의 명사 묶음. 쉼표·말줄임표(`…`, `...`)를 건너뛰는 조합은 만들지 않습니다. 이중 이스케이프된 HTML 엔티티(`&amp;hellip;` 등)는 풀어서 `hellip` 같은 토큰이 생기지 않게 하고, 중복 제거용 해시는 이 정리를 거치지 않습니다.
- **정치 제외**: 정치 분야 피드는 목록에서 뺐고, 다른 분야에 섞인 정치 헤드라인은 `politics_terms.txt` 로 한 번 더 거릅니다. 거른 건수는 `days.csv` 에 남습니다.
- **304 응답**: 서버가 "변경 없음"(304)으로 답해도 피드별로 마지막 최신 기사 시각을 상태에 보관해 24시간을 넘기면 정지 의심으로 셉니다. 보관한 시각이 없으면(상태 유실, 날짜 없는 피드) 판단하지 않습니다.
- **상태**: 수집 중간 상태(해시·키워드·매체)는 git이 아니라 Actions **캐시**에 둡니다. 헤드라인이 git 기록에 영구히 남지 않게 하려는 것입니다.
- **확정된 날의 기사 무시**: 확정한 날에 발행된 기사가 36시간 창에 남아 다시 들어오면 확정 파일을 덮어쓰므로 건너뜁니다(`closed`). 이미 확정된 날의 낙오 기사만 상태에 남았을 때도 파일을 덮어쓰지 않습니다.
- **날 확정**: 오늘·어제는 열려 있어 상태에서 매번 다시 계산하고(중복 집계 없음), 이틀 지난 날부터 `data/` 에 파일로 확정해 커밋합니다. 커밋은 하루 한 번 정도입니다.
- **별칭**: 띄어쓰기·대소문자만 다른 표기(`두바이쫀득쿠키` = `두바이 쫀득 쿠키`)는 저장할 때 합칩니다. 줄임말(`두쫀쿠`)은 원자료를 건드리지 않고
  `alias_map.json` 에만 기록하며, 분석할 때 `radar.alias.apply_alias_map()` 으로 합칩니다. 잘못 합쳤으면 그 줄을 지우면 됩니다. 모든 병합은 `merge_log.csv` 에 남습니다.

## 저장 기준과 표시 기준

- **저장**: 하루 기사 1건뿐인 키워드도 일일 파일에 남깁니다 (`min_articles_to_store: 1`). 헤드라인 원문을 보관하지 않으므로 한 번 버린 1건 키워드는 되살릴 수 없고, 1건 등장이 바로 초기 신호이기 때문입니다.
- **표시**: 화면·분석에서 보여 주는 기준은 따로 둡니다 (`min_articles_to_display: 2`). `radar.store.read_daily(data_dir, day, min_articles=2)` 처럼 읽을 때 적용합니다.
- **최초 등장일**: `radar.store.first_seen(data_dir)` 가 일일 파일을 날짜순으로 훑어 키워드별 첫 등장일을 돌려줍니다. 일일 파일에 이미 모든 키워드가 있어 별도 색인 파일은 두지 않았습니다. 기록이 시작된 첫날 나온 키워드는 그 전부터 있었을 수 있습니다.
- **용량**: 1건짜리가 많아 행 수가 늘어나므로 gzip 으로 저장합니다. 첫 날이 확정되면 `data/daily/` 파일 크기를 확인하세요. 너무 크면 `min_articles_to_store` 를 올리거나 1건짜리 3어절 조합만 거르도록 조정할 수 있습니다 (올리는 것은 쉽지만 낮춰서 과거를 되살릴 수는 없습니다).

## 장애를 하락으로 오인하지 않는 장치

날짜마다 `days.csv` 에 아래 기준으로 **완전한 날 / 불완전한 날**을 기록합니다. 불완전한 날은 기준선과 급증 계산에서 뺍니다.

| 플래그 | 뜻 |
|---|---|
| `coverage_low` | 정상 수집한 피드 비율이 70% 미만 (정지 의심 피드는 정상으로 세지 않음) |

| `runs_low` | 하루 6회 미만 실행 (예약 실행 누락) |
| `volume_low` | 기사 수가 최근 완전한 날들의 중앙값의 절반 미만 |
| `state_reset` | 캐시 상태가 사라져 새로 시작함 |
| `gap_long` | 그날에 걸친 가장 긴 수집 공백이 6시간(`max_gap_hours`)을 넘음. 공백 동안 RSS 에서 밀려난 기사를 놓쳤을 수 있음 (`days.csv` 의 `max_gap_h`) |
| `gap_unknown` | 공백 기록이 시작되기 전의 날(기록 시작 이전, 또는 상태 유실 직후). 공백이 길었는지 알 수 없어 기준선에서 뺌 |

완전한 날이 **21일** 쌓이기 전에는 `scripts/status.py` 가 급증 판정을 "보류"로 표시합니다. robots.txt 가 막은 피드는 장애로 세지 않고 수집에서 제외합니다.

## 예약 실행 구성

GitHub 의 `schedule`(cron)은 지연·누락될 수 있어(관측: 매시간 설정에도 6시간 공백) **두 개의 트리거**를 함께 씁니다.

| 트리거 | 설정 | 비고 |
|---|---|---|
| GitHub schedule | `.github/workflows/collect.yml` 의 `17 * * * *` | 기본. 지연·누락 가능 |
| 외부 스케줄러 (cron-job.org) | 매시 47분, `workflow_dispatch` 호출 | 보조. 합치면 약 30분 간격 |

두 트리거가 겹쳐도 `concurrency: collect` 와 기사 중복 제거 때문에 데이터는 꼬이지 않습니다.

**외부 스케줄러 설정값** (토큰 값은 저장소에 절대 쓰지 않습니다. 저장소가 public 입니다.)

- URL: `https://api.github.com/repos/Shintm7/Korea-Trend-Dashboard/actions/workflows/collect.yml/dispatches`
- Method: `POST`, Body: `{"ref":"main"}`
- Headers: `Authorization: Bearer <토큰>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `Content-Type: application/json`
- 정상 응답: HTTP **204**
- 토큰: fine-grained PAT, 이 저장소만, 권한 Actions **Read and write**(Metadata read 자동). 만료일이 지나면 외부 호출이 401 로 실패하므로 만료 전에 새로 발급해 cron-job.org 에서 교체합니다.
- API 버전 `2022-11-28` 은 GitHub 안내상 2028-03-10 종료 예정입니다. 그 전에 새 버전 값으로 교체합니다.

**확인 방법**: Actions 목록에서 Event 가 `workflow_dispatch`(외부)·`schedule`(GitHub)인 실행이 번갈아 생기는지 봅니다. 외부 호출이 멈추면 `days.csv` 의 `max_gap_h` 와 `gap_long` 으로 드러납니다.

## 표시 계층 (원본과 분리)

원본(`data/daily`)은 그대로 두고, 화면에 보이는 방식만 `radar/display.py` 가 읽을 때 정리합니다. 규칙은 `config/display.yaml`(버전 기록)에 있습니다.

- **포함 관계 그룹**: 구절 키워드가 구성 단어와 기사 수가 *같을 때만* 한 줄로 보여 줍니다(대표어는 긴 구절). 원본 키워드의 시계열은 합치거나 짧은 키워드로 대체하지 않습니다. 그룹의 기사 수는 구성 키워드 중 최댓값이고(합 아님), `member_series()` 로 키워드별 추이를 따로 읽습니다.
- **단일 매체 템플릿**(매체 1곳, 기사 8건 이상): 제외하지 않고 순위 점수만 0.25배로 낮춥니다.
- **장소 뒤 `서`**: `config/places.txt` 의 장소 이름 뒤에 붙은 경우만 표시용으로 뗍니다(`뉴욕서`→`뉴욕`). 보고서·청구서 같은 단어는 건드리지 않습니다.

급증 판정·품질 판정·장기 분석은 이 계층을 쓰지 않고 원본 집계를 직접 읽습니다(테스트로 보장). `python scripts/preview.py --day 날짜` 로 결과를 볼 수 있습니다.

## RSS 출처 감사 (수동 실행)

현재 활성 피드와 공개 목록의 신규 후보를 같은 방식으로 측정해, 어떤 피드가 새로운 주제를 얼마나 가져오는지 비교하는 읽기 전용 도구입니다. **피드 목록·수집 설정·`data/` 를 바꾸지 않고, 신규 후보를 수집 대상에 넣지 않습니다.** 수집 워크플로(`collect.yml`)와 별개로 실행되며, 저장소 쓰기 권한이 없습니다.

**실행 방법**: GitHub 저장소 → **Actions** 탭 → 왼쪽 목록의 **Audit RSS sources** → **Run workflow** (브랜치 main) → 초록색 **Run workflow**. 보통 3~10분 걸립니다. 끝나면 그 실행 화면에서
- 아래쪽 **Summary** 에 보고서가 그대로 표시되고,
- 맨 아래 **Artifacts → `audit-report`** 를 내려받으면 `audit_report.md`(보고서), `audit_feeds.csv`(피드별 측정값), `audit_distribution.csv`(매체·분야 분포)가 들어 있습니다. 보관 기간 30일.

**측정 항목**: HTTP 상태, 응답 시간, XML 파싱, 최신 기사 시각, 최근 기사 수, 한글 비율, 정치 기사 비율, 시간대 어긋남 의심. **중복률**은 정규화 제목 해시 일치(같은 기사)와 핵심 단어 겹침(같은 사건)으로 계산하고, 후보는 현재 62개 피드 전체와, 현재 피드는 다른 매체 피드와 비교합니다. **추가 가치 순위**는 기존 피드와 앞서 고른 후보를 모두 반영하고도 남는 순수 신규 기사 수 순입니다.

**정책**: 기존 수집과 같은 `HttpFetcher` 를 씁니다(robots.txt 확인, 같은 서버 최소 1초 간격, 타임아웃 20초, 재시도 1회, 같은 사용자 에이전트). 헤드라인 원문은 메모리에서 해시·키워드로만 쓰고 보고서·로그·산출 파일 어디에도 넣지 않습니다. 판정 기준은 `config/audit.yaml` 에 있습니다.

한 시점의 스냅샷이므로 시간대를 달리해 두 번 실행해 비교하는 것을 권합니다. 결과를 보고 피드를 추가할지는 별도로 승인한 뒤 `feeds.yaml` 을 바꿉니다.

## 이용 조건 관련

- 요청 전에 서버별 `robots.txt` 를 확인하고, 막힌 주소는 가져오지 않습니다. 같은 서버에는 1초 이상 간격을 두고, 변경이 없으면 `304` 로 받습니다.
- 공개하는 것은 키워드별 건수뿐이고 헤드라인·링크·본문은 저장하지 않습니다.
- 언론사별 RSS 이용 약관을 법적으로 검토한 것은 아닙니다. 피드 안의 저작권 문구와 robots.txt 만 확인했습니다.

## 알아둘 점

- 급증 판정은 **아직 구현하지 않았습니다.** 이번 단계는 수집·집계·품질 기록까지이고, 기준선이 쌓인 뒤 다음 단계에서 만듭니다.
- GitHub 예약 실행은 몇 분에서 수십 분 늦을 수 있습니다. 공개 저장소는 60일 동안 활동이 없으면 예약 실행이 꺼지는데, 하루 한 번의 데이터 커밋이 활동으로 인정되는지는 확인하지 못했습니다.
- 캐시를 수동으로 지우면 그 시점까지의 열린 날 데이터가 사라지고 `state_reset` 으로 표시됩니다.
- 로컬 실행: `pip install -r requirements.txt` 후 `python -m unittest discover -s tests`, `python scripts/simulate.py`.

## RSS 감사 도구 사용 시 주의

- 감사 워크플로(`.github/workflows/audit.yml`)는 **수동 실행 전용**이며 읽기 전용입니다. `feeds.yaml` 과 `data/` 는 바뀌지 않습니다.
- 수집 워크플로는 **매시 17분과 47분**에 실행됩니다. 이 시각 근처에 감사를 수동으로 실행하면 같은 호스트에 대한 요청이 겹칠 수 있으므로 가급적 피하십시오.
- 감사 결과는 한 시점의 스냅샷입니다. 단일 결과만으로 피드 추가·제외를 결정하지 말고 다른 시각대에 한 번 더 실행해 비교하십시오.
