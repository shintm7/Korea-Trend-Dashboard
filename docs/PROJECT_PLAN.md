# 프로젝트 방향 및 향후 계획

> 문서 상태: 기획 기록. 아래 항목은 현재 구현 상태와 구분한다.
> 마지막 정리: 2026-11-27

## 1. 프로젝트 목적

한국에서 관심이 커지는 주제와 소비·생활 아이디어를 발견하고, 관심의 변화·지속성·재등장을 장기적으로 관찰하는 개인용 트렌드 레이더다. 투자 또는 사업 의사결정 도구가 아니다. 기본 운영 원칙은 무료·저비용이며, 유지보수 복잡도를 낮게 유지한다.

## 2. 현재 구현과 향후 계획의 구분

### 현재 구현된 기반

- RSS 뉴스 헤드라인 수집과 키워드 추출·일일 집계
- 날짜별 수집 품질 기록 및 피드별 health 기록
- 키워드 표기 정규화와 명시적 alias 관리
- 불완전한 날짜를 기준선·급증 판정에서 제외하는 품질 보호
- 21개의 완전한 날이 쌓이기 전 급증 판정을 보류하는 기준
- RSS 출처 감사 도구(수동·읽기 전용)

세부 구현 상태와 실행 방법은 README 및 코드가 기준이다. 이 문서의 계획을 구현 완료로 해석하지 않는다.

### 아직 구현되지 않은 계획

- 별도의 데이터 품질 진단·기초 분석 도구
- 트렌드 지속성·재등장 분석
- 네이버 쇼핑인사이트와 뉴스 키워드의 비교 분석
- 최종 대시보드 화면 및 장기 트렌드 탐색 기능

급증 탐지 알고리즘의 개선은 기준선 데이터 분석 이후 검토한다. 이 문서는 해당 기능이 이미 구현됐다고 주장하지 않는다.

## 3. 핵심 설계 원칙

### 3.1 서로 다른 평가 축을 합치지 않는다

다음 항목은 별도로 평가한다.

- 데이터 신뢰성: 수집 완전성, 피드 상태, 누락·장애
- 키워드 품질: 추출 노이즈, 중복 표현, 매체 편중
- 트렌드 특성: 지속성, 재등장, 매체 다양성
- 소비 관심: 네이버 쇼핑인사이트 검색 관심의 변화
- 급증 여부: 기존 뉴스 기반 탐지 로직의 결과

서로 다른 의미의 지표를 임의로 합산해 단일 종합점수로 만들지 않는다.

### 3.2 키워드 동일성

- 공백·대소문자 등 명백한 표기 차이만 제한적으로 자동 정규화한다.
- 의미상 동일한 표현은 명시적으로 관리되는 alias를 통해서만 연결한다.
- 불확실하거나 세부 대상이 다른 표현은 별도로 유지한다.
- 접미사·단어를 광범위하게 제거하거나 AI가 의미만으로 자동 병합하지 않는다.
- 과거 집계 데이터의 소급 변경은 기본적으로 하지 않는다. 필요하면 별도 영향 분석과 승인을 거친다.

### 3.3 뉴스와 쇼핑인사이트의 관계

- 뉴스는 사회적 관심 및 이슈 후보를 발견하는 주 신호다.
- 네이버 쇼핑인사이트는 발견된 주제의 소비 관련 검색 관심을 확인하는 보조 신호다.
- 정확히 일치하거나 승인된 alias로 연결되는 검색어만 비교한다.
- 의미상 관련성이 있다는 이유만으로 자동 연결하지 않는다.
- 쇼핑인사이트의 상대 지수와 뉴스 기사량을 합산하거나 직접적인 절대량 비율로 해석하지 않는다.
- 두 신호의 변화 방향과 시차를 나란히 비교한다. 검색 관심은 구매량·매출과 동일하지 않다.

## 4. 데이터 품질 및 수집 안정성

### 데이터 품질 평가

기존 급증 탐지와 별도로 데이터 신뢰성을 평가한다. 품질 문제를 트렌드의 중요도나 급증 점수와 혼합하지 않는다. 수치 임계값은 기준선과 실제 데이터 분포를 확인한 뒤 정한다.

### 피드 장애 대응

기본 원칙은 일시적인 오류만으로 수집 구조를 바꾸거나 피드를 자동 비활성화하지 않는 것이다. 기존 Actions 로그와 health CSV를 우선 활용하며, 별도의 복잡한 모니터링 시스템이나 알림 시스템은 현재 범위에 넣지 않는다.

다음은 검토를 시작하기 위한 잠정 운영 기준이며, 코드에 반영된 자동 정책이 아니다.

- 단발성 실패: 기록하고 관찰
- 동일 피드 3회 연속 실패: 원인 조사 후보
- 2일 이상 반복 실패: 개선 필요성 검토
- 동일 매체의 여러 피드 동시 실패: 매체 단위 원인 조사
- 피드 형식 변경·파싱 실패 반복: 수집기 수정 검토

robots_unavailable(robots.txt 확인 불가)과 robots_blocked(접근 차단 확인)는 구분한다. 확인 불가를 명시적 차단으로 간주하지 않는다. 자동 비활성화·복잡한 재시도 도입은 현재 계획에 없다.

## 5. 데이터 분석 계획

### 21일 완전 기준선 이후 첫 분석

첫 분석은 알고리즘 튜닝보다 데이터 진단에 집중한다.

1. 날짜별 완전성 및 수집량 확인
2. 키워드 추출 노이즈·중복·일반어 분포 확인
3. 매체 집중도와 매체 다양성 확인
4. 키워드의 활성 일수·지속 기간·재등장 현상 확인
5. 기존 급증 탐지 결과의 기초 검토
6. 네이버 쇼핑인사이트 비교는 내부 데이터 진단 이후 별도 단계로 수행

21일은 초기 기준선이지, 계절성이나 장기 트렌드를 확정하기에 충분한 기간이 아니다. 초기 결과만으로 임계값을 최적화하거나 과거 데이터를 재작성하지 않는다.

### 분석 도구의 형태

- 기존 수집 파이프라인과 분리된 읽기 전용 분석 스크립트를 우선한다.
- 기존 data 원본을 수정하지 않는다.
- 분석 결과는 수집 데이터 디렉터리와 분리해 Markdown 보고서 중심으로 남긴다.
- 상세 CSV는 실제 필요성이 확인될 때만 만든다.
- 별도 데이터베이스, 대시보드형 분석 플랫폼, 자동 보고서 발행은 현재 범위에서 제외한다.

## 6. 관찰 기간과 트렌드 수명

기준선 완성 후 동일한 분석 방법을 유지하며 중간 점검을 진행한다.

| 시점 | 목적 | 해석 범위 |
|---|---|---|
| 21일 | 초기 기준선 | 데이터 상태와 기초 분포 |
| 30일 | 첫 중간 점검 | 단기 반복성 |
| 60일 | 두 번째 중간 점검 | 중기 지속성과 재등장 |
| 90일 | 첫 장기 평가 | 지속 기간과 반복 패턴의 초기 관찰 |

30일·60일은 중간 점검이고 90일을 첫 장기 평가 시점으로 삼는다. 분석 항목과 계산 방법을 기간마다 임의로 바꾸지 않는다.

계절성은 90일만으로 확정하지 않는다. 최소 12개월의 관찰과 전년 동기간 비교를 통해 초기 검증하고, 2년 이상 자료가 쌓이면 연도별 반복성을 비교한다.

### 트렌드 수명 지표 후보

- 최초 발견일과 마지막 등장일
- 활성 일수와 전체 지속 기간
- 급증 횟수 및 재등장 여부

지속 기간(최초~마지막 등장 사이의 기간)과 활성 일수(실제 활동이 확인된 날짜 수)는 구분한다. 초기에는 5단계 수명 상태를 확정적으로 분류하거나 예측 모델을 만들지 않는다. 데이터가 충분해진 뒤 발견·급증·지속·쇠퇴·재등장 상태 분류를 검토한다.

## 7. 최종 사용자 화면의 정보 구조(기획)

향후 화면은 다음 세 영역을 중심으로 검토한다.

1. 오늘의 트렌드: 새롭게 급증한 키워드, 지속 관심 키워드, 매체 다양성, 최근 변화
2. 키워드 상세: 날짜별 기사량, 최초 발견일, 활성 일수, 매체 수, 쇼핑 관심도, 관련 원문 링크
3. 장기 트렌드: 30·60·90일 변화, 재등장, 지속 기간, 장기 계절성

이는 화면 기획안이며 현재 구현된 UI가 아니다. 실제 화면 구현은 기준선 분석으로 유용한 지표를 확인한 뒤 진행한다. 급증·지속성·데이터 신뢰성·쇼핑 관심을 단일 순위나 종합점수로 혼합하지 않는다.

## 8. 기능 범위

### 유지할 핵심 방향

- RSS 기반 후보 발견
- 키워드 추출·정규화 및 일별 데이터 축적
- 데이터 품질 평가
- 뉴스 기반 급증 탐지(기준선 검증 이후)
- 트렌드 지속성·재등장 분석
- 네이버 쇼핑인사이트를 통한 소비 관심 보조 검증

### 제외 또는 보류

| 항목 | 결정 | 근거 |
|---|---|---|
| YouTube API 수집·통계 분석·임베드/증거 패널 | 제외 | 정책 제약과 유지 부담에 비해 효용이 낮음 |
| 나무위키 자동 수집 | 보류 | 현재 정보 공백이 확인되지 않음 |
| AI 의미 기반 자동 키워드 병합 | 제외 | 오분류 위험과 운영 복잡성 |
| 복잡한 트렌드 예측 모델 | 보류 | 장기 데이터 부족 |
| 자동 뉴스 요약·해석 | 보류 | 핵심 기능보다 우선순위 낮음 |
| 별도 데이터베이스 | 제외 | 현재 CSV 기반 구조 유지 |
| 실시간 알림 시스템 | 보류 | 효용이 확인되지 않음 |
| 복잡한 대시보드 UI | 보류 | 실제 분석 결과 확인 후 결정 |

보류 항목은 자동으로 다음 단계에 포함되지 않는다. 실제 데이터에서 명확한 필요성이 확인되고 별도 승인을 받은 경우에만 재검토한다.

## 9. 데이터 계보(Data Lineage) — 후속 검토

일별 데이터의 재현 가능성을 높이기 위해 날짜별 품질 기록(days.csv)에 최소한의 생성 환경 정보를 기록하는 방안을 검토한다.

후보 필드:
- 수집·집계에 사용된 코드 커밋 SHA
- 형태소 분석기(kiwipiepy) 버전
- alias 정의의 식별 해시

아직 구현 결정이 아니다. 실제 확정 시점의 실행 환경에서 버전과 alias 입력 파일 범위를 확인하고, 기존 기록을 소급 수정하지 않는 방식으로 설계한다. 피드별 실행 진단용 health CSV에는 파이프라인 계보 정보를 섞지 않는다.

## 10. 향후 우선순위

1. 기존 수집 체계를 안정적으로 유지하고 21일 완전 기준선을 확보한다.
2. 기준선 이후 읽기 전용 데이터 품질·기초 분석을 수행한다.
3. 분석 결과를 검토해 지속성·재등장 지표의 정의를 구체화한다.
4. 필요성과 데이터 연결 가능성을 확인한 뒤 쇼핑인사이트 비교를 진행한다.
5. 분석에서 검증된 정보 구조를 바탕으로 대시보드를 설계한다.
6. 90일 관찰 후 장기 트렌드 분석을 평가한다.

모든 구현은 별도 작업 범위 승인, 브랜치, PR, 검토 절차를 따른다. main 직접 push와 자동 merge는 금지한다.
